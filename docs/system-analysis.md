# Системный анализ афиши театров

## Назначение и границы

Система помогает зрителю найти показ и получить билет на категорию мест, а администратору — вести расписание и просматривать оформленные билеты. Описание относится к версии портфолио, а не ко всем пожеланиям из курсовой. Доступный остаток мест — ресурс конкретного показа и категории.

## Роли

| Действие | Гость | Зритель | Администратор |
|---|---|---|---|
| Регистрация и вход | Да | После выхода | После выхода |
| Афиша, оформление своего билета, отзывы | Нет | Да | Не выведено в административный интерфейс |
| Свои билеты и возврат | Нет | Да | Не выведено в административный интерфейс |
| Просмотр всех билетов и добавление показа | Нет | Нет | Да |

`is_admin` выбирает интерфейс после входа. Прикладной сервис отдельно проверяет право администратора и владельца билета. Это не защита от человека с прямым доступом к учётной записи PostgreSQL.

## UC01 Оформить билет

Предусловия: зритель вошёл; показ ещё не начался; категория создана.

1. Зритель выбирает показ в афише и категорию места.
2. Приложение показывает текущий остаток. Он информационный: другой зритель может купить место до подтверждения.
3. Зритель нажимает «Купить». Сервис проверяет текущую учётную запись и отправляет INSERT билета.
4. Триггер проверяет время показа и условным UPDATE увеличивает `SoldSeats`, только если `SoldSeats < TotalSeats`.
5. PostgreSQL создаёт билет, транзакция фиксируется. Приложение обновляет остаток и показывает результат.

Альтернативы: мест нет или показ начался — понятное сообщение, билет не создаётся; ошибка ограничения или связи — вся транзакция откатывается, счётчик не меняется; нет авторизации — операция не выполняется. Деньги не списываются: платёжная интеграция отсутствует.

## UC02 Вернуть билет

Предусловия: вошёл владелец активного билета; показ ещё не начался.

1. Зритель открывает свой билет и подтверждает возврат.
2. Сервис обновляет строку только с совпадающими ID билета, ID текущего клиента и статусом `active`.
3. Триггер проверяет время показа, меняет счётчик и устанавливает время возврата. Транзакция фиксирует обе операции.
4. Билет остаётся в истории как `cancelled`, место вновь доступно.

Повторный возврат, чужой или отсутствующий билет не уменьшают счётчик. После начала показа возврат запрещён. Физическое удаление билетов запрещено триггером.

## UC03 Добавить показ

Администратор вводит точные названия постановки и театра, будущую дату и время. Сервис проверяет, что постановка относится к указанному театру. Создание показа и трёх категорий выполняется одной транзакцией. Дубликат постановки/даты/времени и недопустимая вместимость отклоняются. При ошибке категории не остаётся «пустого» показа. Номер зала пока фиксирован: 1.

## Правила и критерии приёмки

| ID | Правило | Проверяемый результат |
|---|---|---|
| BR01 | Остаток неотрицательный | Из двух одновременных запросов на последнее место успешен ровно один |
| BR02 | Изменения билета и счётчика атомарны | Ошибка INSERT откатывает увеличение счётчика |
| BR03 | Возврат только владельцем и один раз | Чужой/повторный запрос не меняет остаток |
| BR04 | История не удаляется | Возвращённая строка сохраняет ID и время возврата |
| BR05 | Один отзыв на постановку от клиента | UNIQUE отклоняет второй отзыв; CHECK отклоняет оценку вне 1–10 |
| BR06 | Логин уникален без учёта регистра | Нормализация + UNIQUE не допускают Demo/demo |
| BR07 | Показ и места создаются целиком | Ошибка последней категории откатывает весь показ |
| BR08 | Прошедший показ недоступен для покупки | Проверяется в PostgreSQL, включая прямой INSERT |

## Нефункциональные требования

Секреты подключения не входят в репозиторий. Пароли не сохраняются открытым текстом. Ошибки PostgreSQL преобразуются в сообщения без реквизитов подключения. Транзакции автоматически откатываются, соединения закрываются. Клиент и БД должны работать в одной локальной часовой зоне; для Docker задана Europe/Moscow. Производительность и доступность под промышленной нагрузкой не измерялись.

## Архитектура

`PyQt5 forms → db.py (session, validation, transactions) → psycopg2 → PostgreSQL (constraints, ticket trigger)`.

REST API и микросервисы не реализованы. Для следующей итерации: API вместо прямого подключения, серверные сессии, журнал действий администратора, отдельные роли БД, расписание залов с проверкой пересечений.
